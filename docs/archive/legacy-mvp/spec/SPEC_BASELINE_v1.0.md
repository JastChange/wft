# WFT MVP 规格基线 v1.0

> 状态：Approved for Implementation
>
> 日期：2026-08-03
>
> 产品：批次式 Linux 节点巡检与知识沉淀工具

## 1. 产品目标

在当前 Mac 控制机上，通过一条命令或本地定时任务，对多台 Linux 节点执行只读巡检脚本；自动识别异常，生成规则/AI 摘要，把历史结果保存在 SQLite，并单向导出到本机 Obsidian Vault；异常批次发送 webhook 通知。

MVP 实机验收环境为 5 台 Linux 节点。50 端点只做模拟容量测试；未完成 50 台真实节点测试前，不宣称已获 50 台真实环境认证。

## 2. MVP 范围

### 2.1 必须包含

- YAML 节点清单校验、group/tag 选择和凭据引用；
- 主机指纹发现、可信渠道核对、人工确认与审计；
- 默认 50 并发、连接速率限制、超时、失败隔离和有界重试；
- 只读脚本注册、完整 SHA-256 身份、上传/执行与结果追溯；
- stdout/stderr 小内容内联、大内容 blob，统一哈希和大小限制；
- Run/Batch/Node 三层状态、checkpoint、stale Run 同 run_id 恢复；
- 健康结果不调用 LLM，异常才进入 T1/T2；LLM 失败降级为规则摘要；
- SQLite WAL 权威存储、幂等写入、历史查询和 transactional outbox；
- Obsidian 单向导出、managed/free 分区、幂等重建；
- 本地 scheduler、结构化日志、审计、doctor；
- 异常 webhook 通知，健康批次不通知；
- CLI 统一退出码 0/1/2。

### 2.2 明确不包含

- 修改服务器配置或业务数据的脚本；
- 实时监控、部署编排、远端 agent；
- Web 管理后台、多人权限、SSO/RBAC；
- Windows、网络设备、节点自动发现；
- AI 自动修复；
- Obsidian → SQLite 反向同步；
- PostgreSQL、Redis、Celery、分布式调度；
- LLM 费用预算和价格门禁；
- 业务输出敏感信息脱敏。

## 3. 已接受的风险与使用边界

- MVP 不脱敏，异常输出可能原样写入 SQLite、日志、Obsidian，并发送给云端 LLM。
- 用户不得让巡检脚本输出密码、Token、私钥等秘密；数据不能出域时使用本地 LLM 或关闭 LLM。
- 配置仍只允许凭据引用，不允许把秘密正文写入仓库。
- 所有脚本必须是 `read_only`；非只读脚本在注册阶段拒绝。
- 恢复语义是至少一次。UNKNOWN 节点可重新执行，因此脚本必须可安全重复运行。

## 5. 接口与数据原则

- 跨模块对象必须匹配 Contract-01～12；禁止私传未登记字段。
- 完整 SHA-256 是脚本唯一身份；短哈希只展示。
- `execution_uid` 重试不变，`attempt_id` 每次尝试不同。
- 同一 idempotency_key + 相同参数返回已有 Run；相同 key + 不同参数拒绝。
- 业务结果提交与 outbox 事件必须在同一 SQLite 事务中完成。
- 终态不可回写；补偿成功只更新导出/通知回执。
- 错误名称、是否重试和告警级别以全局错误矩阵为准。

## 6. 发布门禁

实现完成后：

- 运行 `验收矩阵_5节点_v0.1.md` 的 AC-001～017 和 AC-008B；
- 通过 PERF-001、PERF-003、PERF-004；PERF-002 记录结果和瓶颈，不冒充 50 台真实环境；
- 12 个 schema 各有正常、边界、错误样本并进入 CI；
- 任一数据丢失、未经确认写入主机指纹、非只读脚本被接受、凭据正文进入仓库，均一票否决；
- @OpenCoder 报告自动化测试和规格偏差；
- @GeminiOps 报告当前 Mac、5 节点、Docker/CI 和模拟容量环境的复现结果；
- 需求方根据实际验证结果决定是否发布。

## 7. 实施前仍需配置但不阻塞代码初始化

- Obsidian Vault 的绝对路径；
- LLM 模式：关闭、本地或具体单一供应商；
- webhook：本地 stub 或真实通道；
- 5 台 Linux 的 inventory 和凭据引用。

这些值不得提交真实秘密到仓库。

## 8. 变更控制

实现代理发现无法按规格实现时，必须报告“规格偏差”，不能自行改变范围、状态、错误、契约或验收标准。由 @SpecArchitect 更新规格并取得需求方确认后再继续。
