## 2. 产品目标

WFT 帮助单个诊断操作员在一台 Linux 控制服务器上，对一个或多个 Ubuntu 节点执行可信的只读检查。产品支持两种任务：

- **安装验证**：验证新安装的操作系统是否符合预期；
- **故障诊断**：收集判断故障原因所需的完整证据，不自动修复。

交付优先级为：核心证据采集 → 只读结果页 → Webhook → AI 分析 → Obsidian 问题笔记。

## 3. 用户与部署边界

- 只有一个诊断操作员；不支持注册、多用户、角色或 RBAC。
- 正式运行环境是一台 Linux 控制服务器，使用 Docker Compose。
- 操作员通过 SSH 登录控制服务器运行 CLI。
- Web 只面向内网/VPN，使用 HTTP；首版不提供 HTTPS。
- Web 仅查看，不得创建、取消、分析、导出或删除任务。
- 只支持手动任务；不提供 Scheduler 或后台自动恢复。

## 4. 功能需求

### FR-001 管理员认证

- CLI 必须能生成初始管理员密码并重置密码。
- 服务端只保存 Argon2 密码哈希。
- 登录后 Cookie 只保存随机 Session ID，并设置 HttpOnly。
- HTTP 明文传输风险已接受；不得因此改为在服务端保存明文密码。

### FR-010 节点清单

- 节点清单由操作员在控制服务器本地 YAML 中维护。
- 每个节点必须包含：操作员提供的节点名、主机、端口、用户名、私钥绝对路径、启用状态、group 和 tag。
- 私钥文件可由 YAML 引用，但私钥正文不得进入任务记录、日志、Web 页面或 Git 仓库。
- 首版仅支持私钥文件认证和 Ubuntu 22.04/24.04 目标节点。
- 一次任务必须支持：显式节点、group、tag、全部启用节点。
- 任务创建时必须保存节点连接信息快照；后续修改清单不得改变历史记录。

### FR-020 脚本源与 Manifest

- 诊断脚本位于独立 Git 仓库和配置的分支。
- 控制服务器使用只读 Deploy Key；配置仅保存权限为 `0600` 的私钥文件路径。
- WFT 直接信任配置的仓库 URL 和分支，不验证 commit/tag 签名。
- 每次任务开始前必须尝试拉取远端最新提交。
- 拉取失败时，CLI 必须显示缓存 commit、提交时间和来源，并允许：
  - 交互式确认使用缓存；
  - 使用显式 `--allow-cached-scripts` 参数确认。
- 无人值守且未显式允许缓存时必须失败。
- 同一任务的所有节点必须使用同一脚本快照。
- 任务必须记录仓库 URL、分支、commit SHA、Manifest 哈希和每个脚本 SHA-256。
- Manifest 必须登记脚本路径、解释器（`bash`、`sh`、`python3`）、超时、成功退出码、只读声明和诊断方案。
- 只允许执行 Manifest 中登记且哈希匹配的脚本。
- 支持单脚本、多脚本和预定义诊断方案。
- “只读”依赖脚本仓库维护者审核；WFT 不做静态阻断、沙箱或权限降级，允许 root/sudo 账号。

### FR-030 任务创建与选择

- 创建任务时必须选择 `installation_validation` 或 `fault_diagnosis`。
- 每次创建必须生成新的任务 ID；失败或中止后重新执行也不得关联或恢复旧任务。
- 默认节点并发为 10，可配置范围为 1–50。
- 同一节点的脚本按 Manifest/诊断方案顺序串行执行；不同节点并发执行。
- 一个节点或脚本失败不得取消其他节点。
- WFT 不自动重试 SSH 连接、节点或脚本。

### FR-040 SSH 执行

- 使用 SSH/SFTP 上传脚本到任务专用远端临时目录。
- 首次连接无条件接受目标返回的 Host Key，并在任务记录中保存实际指纹。
- 执行前确认目标存在 Manifest 指定的解释器。
- 脚本超时时必须终止该脚本、记录 `TIMEOUT`，并继续当前节点后续脚本。
- 脚本执行后必须尽力删除整个远端临时目录；清理失败单独记录，不能覆盖脚本结果。
- 每个脚本必须按 Manifest 的成功退出码判定检查结果。

### FR-050 状态、结论和退出码

- 任务状态只能是：`PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`CANCELLED`。
- 任务执行状态与诊断结论必须分离。
- 安装验证的节点结论只能是：`PASS`、`FAIL`、`INCONCLUSIVE`。
  - 全部检查完成且符合成功条件：`PASS`；
  - 检查完成并发现不符合项：`FAIL`；
  - 因连接、解释器或系统错误无法完成判断：`INCONCLUSIVE`。
- 故障诊断完成只表示证据已收集，不表示找到根因或节点健康。
- Ctrl-C 等主动终止必须把未完成任务标记为 `CANCELLED`。
- 控制服务器崩溃后，下一次启动必须把残留 `RUNNING` 任务标记为 `FAILED`，不得恢复。
- 已完成节点结果必须保留；未完成节点标记为 `CANCELLED` 或相应失败状态。
- CLI 退出码：
  - `0`：任务完成且没有诊断问题；
  - `1`：任务完成但发现问题，或安装结论为 `FAIL/INCONCLUSIVE`；
  - `2`：配置错误、任务未完成或系统故障。

### FR-060 权威文件存储

- 权威记录由版本化 JSON 和独立原始文件组成；不得以 SQLite 作为权威源。
- stdout、stderr、应用日志、SSH 阶段日志和错误堆栈必须完整保留，不设产品级大小上限。
- WFT 自身不得主动记录管理员密码、SSH 私钥、Deploy Key 或 AI Key。
- 诊断脚本必须保证不输出密码、Token 或私钥；WFT 不检测或脱敏脚本输出。
- 每个 JSON 必须包含 `schema_version`。
- JSON 更新必须使用同目录临时文件、flush/fsync 和原子重命名。
- 节点/脚本结果必须独立提交，使任务中止时已完成证据仍可读取。
- 记录默认永久保留，不自动过期。
- 首版不提供备份或旧版本数据迁移。
- CLI 删除必须二次确认并要求输入原因，但删除完成后不保留 tombstone 或审计记录。
- 磁盘空间不足时当前任务失败并拒绝新任务；不得自动删除历史记录。

### FR-070 只读 Web

- Web 使用 FastAPI、服务端模板和少量 JavaScript。
- 仅支持最新 Chrome/Edge 桌面版。
- 页面必须包含登录、任务列表、状态汇总、实时进度、筛选、节点详情、脚本详情、问题与分析展示、原始文件下载和通知状态。
- 筛选至少支持时间、节点、脚本和状态。
- 页面通过只读 HTML Fragment Endpoint 每数秒轮询实时状态。
- 除登录/登出外，不提供写入路由或公共业务 API。
- SQLite 只用于可删除、可重建的派生查询索引。
- Web 启动时必须检查并增量更新索引；CLI 提供 `wft index rebuild`。
- 索引失败不得修改权威任务目录。

### FR-080 Webhook 通知

- 使用通用 HTTP Webhook。
- 安装验证出现 `FAIL` 或 `INCONCLUSIVE` 时发送。
- 故障诊断完成或中止时发送。
- 通知只包含任务类型、状态、异常节点、脚本、时间和结果页链接。
- 禁止发送 stdout、stderr 或调试日志。
- 每条通知只尝试发送一次；失败后记录失败，不自动或手动重试。
- URL 和认证信息明文保存在权限为 `0600` 且不进入 Git 的私有 YAML。

### FR-090 AI 分析与问题

- AI 只能由操作员运行 `wft analyze <task-id>` 手动触发。
- 可分析安装验证的 `FAIL/INCONCLUSIVE` 和所有故障诊断任务。
- 每个部署只配置一个 OpenAI-compatible HTTP Endpoint。
- AI Key 明文保存在权限为 `0600` 且不进入 Git 的私有 YAML。
- 输入包含节点元数据、脚本信息、stdout、stderr 和相关应用日志。
- 超大输入必须分块分析后合并，并遵守可配置的单次分析预算；权威原始记录不得截断。
- 输出必须是结构化简体中文，包含问题摘要、可能原因、证据引用、置信度和下一步检查；命令、路径和证据保持原文。
- 禁止自动修复或自动执行建议命令。
- AI 请求失败不自动重试；操作员可重新运行并产生新的分析版本。
- 每个分析版本记录模型、时间、输入哈希和提示词版本。
- AI 不可用或输出无效时必须生成规则摘要。
- 无 AI 时，每个失败检查生成一个待分类问题。
- AI 可从成功脚本输出发现问题，也可把同一节点的多个待分类问题归并；不得跨节点归并，且必须保留来源关系。

### FR-100 Obsidian Git 导出

- 使用独立的 Obsidian Vault Git 仓库，WFT 只管理配置的子目录。
- 操作员手动运行 `wft export <task-id>`。
- WFT 可以拉取并修改本地工作树，但不得 commit 或 push。
- Git 冲突时必须停止，不自动解决或强制覆盖。
- 每个诊断问题生成 `WFT/Problems/<节点名>/<问题ID>-<标题>.md`。
- 每个任务另生成一篇索引笔记并链接全部问题。
- 笔记包含任务信息、安装结论/诊断摘要、节点结果表、异常证据、最新 AI 分析和结果页/原始文件链接。
- 重复导出必须幂等；WFT 只更新 managed 区块并保留人工编辑区。

## 5. 非功能需求

### NFR-001 容量

- 支持最多 50 个目标节点。
- 发布门禁使用 50 个模拟 SSH 节点、默认并发 10。
- 固定测试负载必须在 10 分钟内完成，控制服务器进程内存峰值低于 1 GiB。
- 所有节点必须形成终态记录，无结果丢失、无死锁。

### NFR-002 可追溯性

- 任务必须保存节点快照、脚本快照、Host Key 指纹、所有脚本结果、原始输出和分析版本。
- WFT 不提供通用审计日志。
- 删除完成后不保留任何删除记录。

### NFR-003 安全边界

- Web 仅部署于内网/VPN，但使用 HTTP。
- 允许 root/sudo 执行，允许自动接受 Host Key，不验证 Git 签名。
- 以上均为显式接受风险，不得在实现中悄悄声称具备更强安全保证。

### NFR-004 可部署性

- Python 3.12，Typer CLI，FastAPI Web，Docker Compose。
- Web 和 CLI 使用同一个镜像；Web 常驻，CLI 通过 `docker compose run --rm` 按需运行，并共享配置、数据、脚本缓存和派生索引卷。
- 交付物包含源码、测试、镜像构建、Compose、示例配置、部署手册和操作手册。

## 6. 明确不包含

- Scheduler、实时监控、远端 Agent、自动发现；
- 自动恢复、自动诊断任务重试、自动修复；
- Web 写操作、公共业务 API、多用户、RBAC；
- HTTPS、通用审计日志、备份、高可用；
- 内容脱敏、秘密检测、Git 签名验证；
- Webhook 重试；
- 旧 SQLite、旧 YAML 或旧契约迁移；
- PostgreSQL、Redis、Celery、对象存储；
- 真实 50 节点环境认证。

## 7. 已接受但不作为发布测试的风险

- 不限制原始输出大小；
- 不执行大输出、磁盘写满和进程中止故障注入测试；
- 不备份权威文件；
- 删除不留痕；
- HTTP 明文传输；
- root/sudo、自动 Host Key 接受和可变 Git 分支带来的供应链风险。

实现和文档必须准确报告这些边界，不能把未测试行为描述为已验证保证。

## 8. 需求变更

任何状态、退出码、数据字段、安全边界、发布门禁或范围变化，都必须先更新本文、相关 ADR 和验收矩阵并取得确认，再修改实现。
